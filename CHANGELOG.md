# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The quick guide has a History step, and the updater's a Firmware step:** the guides of the flasher, the tester and the updater in the eight languages (portuguese of Portugal) say what the History button shows (the evidence records, newest first, each one checked, filtered by result and text, read only), and the guide of the updater says what the Firmware button does (checks the release signature of an image and opens the Flasher with it selected, writing nothing to a board). `docs/EVIDENCE.md` describes the listing of a folder, the History window and its command line forms, and the Compatibility section of the READMEs says how the notes of a release carry the compatibility table.
- **The updater's security texts follow its new defaults:** the catalog of the updater says that signed commits and the question before the build check are on by default, and the message of a run with nobody to ask names the three ways to answer in advance.
- **A window with the history of the evidence, the same for every program:** `EvidenceHistoryDialog.qml` with its Qt object (`evidence_history_qt.py`) and its texts in the eight languages (`evidence_history_strings.py`, portuguese of Portugal) lists the `urtc-evidence/1` records of a folder newest first, with the kind, the result, the tool, the board, the versions and whether each record still passes its check; a record edited after it was written, a file that is not JSON or a record of another format is shown as not valid with what is wrong. It can be filtered by result, by text and to only the records that fail, reads again each time it opens, shows at most 500 rows (and says how many there are) and changes nothing on disk. `tools/vendor_copy.py` has the sets `history_qt` and `history_qml` for the programs that carry it.
- **The steps of a test plan are worded in the eight languages:** the catalog of the tester has the texts of every message a plan step gives (answers missing, wrong tool, old firmware, value out of range, operator confirmation and the rest), with the portuguese of Portugal.
- **The notes of a release of a program can carry the compatibility table:** `tools/changelog_section.py` (the section of the CHANGELOG of one version, and with `--compat` the generated table of `docs/COMPATIBILITY.md` after it) is now here too, in the set `release_notes` of `tools/vendor_copy.py`, so the flasher, the tester and the updater can print the body of their release the way the firmware repository does; it stops with a message when the version has no section or the table is missing.

## [0.1.0] - Free configuration of a head as a contract, the history of the evidence, the rack reasons in eight languages, a rack simulator that answers like the rack and the lights of Project status following the manifest

- **Free configuration of a head (jumpers `0x1F`) is a contract:** a rack no longer takes that reading for "no tool": it asks the head with `0x1A3`, accepts only an answer that names a tool (`0x1F` and a selection of 1 to 25) and keeps the head in the safe state, with no target and no pre-heat order, until then. `docs/FREE_TOOL.md` fixes the rules (the query, which answers are valid, timeout, attempts, back-off and refresh, and what a change of tool or a lost answer does); `rack_sim` has `classify_jumper`, `parse_free_tool_reply`, `FreeToolConfig`, `FreeToolResolver` and the slot calls `set_slot_jumpers`, `free_tool_step` and `slot_identity`; `conformance/rack_vectors.json` and `generated/rack_vectors.h` carry the jumper readings, the answers and fourteen query scenarios (also across the wrap of the clock) that the rack firmware replays.
- **The lights of Project status follow the evidence of the manifest:** the manifest says how far the repository has been shown to work (`evidence`: `host-test`, `simulator`, `bench` or `field`) and the validator fails when a light is above what that evidence and the maturity allow (`tools/status_lights.py`), so a green that never ran on real hardware cannot come back.
- **A history of the evidence of every program:** `evidence_history` reads a folder of `urtc-evidence/1` records (`.json` and `.jsonl`), checks each one, and lists them newest first with filters (kind, outcome, tool, time, text), a summary and a text, CSV or JSON output; a record edited after it was written, a file that is not JSON or a record of another format is listed as not valid with what is wrong, never skipped. It reads only, and it is part of the `evidence` set that the programs copy. The flasher, the tester and the updater each have a command for it.
- **The rack reasons are worded in the eight languages for the tester and the web studio:** the catalogs of the two programs have the nine reasons of a reply (applied, repeat, wrong length, tool absent, temperature out of range, tool invalid, not heatable, held for coming too soon, unknown command), and the simulator takes the minimum interval between commands as a setting (`min_interval_ms`, 0 = no limit).
- **The rack simulator answers like the rack:** `rack_sim` now writes and reads the reply frame of the rack (an acknowledgement `0x81` for an applied command or a repeat, a refusal `0x82` with the reason: wrong length, tool absent, temperature out of range, tool invalid, not heatable, held for coming too soon, unknown command), holds a second command for one tool that comes within 20 ms of the previous one as the firmware does, and every step of the shared link scenarios in `conformance/rack_vectors.json` carries the reply frame that the rack firmware reproduces byte for byte (two scenarios were added: every refusal with its reason, and a command that comes too soon). `encode_reply` and `parse_reply` are what the programs use to read the answer.

## [0.0.9] - A common evidence format, the compatibility matrix, the firmware file names and the tool identifiers from the spec

- **The names of the files of a firmware release are written once:** `spec/firmware_images.json` holds the pattern of an image name and the files that travel with it, `tools/generate_tools.py` writes `src/urtc_common/firmware_names.py` and `generated/firmwareNames.ts` from it, the compatibility check reads the bundled firmware with it, and the tests compare it with the images of the flasher and with the suffixes the flasher and the web studio use (`vendor_copy.py` sets `firmware_names_ts` and, with the compatibility code, `compat_data`).
- **The tool identifiers are generated for the C repositories too:** `tools/generate_tools.py` writes `generated/urtc_tool_ids.h` (one macro per tool profile, the count, the last profile, the first unassigned value and the free-configuration value) from `spec/tools.json`, `vendor_copy.py` has the set `tool_ids_c`, and the tests compare the numbering with the tool head firmware and with the rack.
- **One shape for the records of the programs:** `urtc_common.evidence` and `spec/evidence.schema.json` define `urtc-evidence/1` (tool, time, subject, transport, files with their hashes, outcome, and a digest of the record) with a strict check that refuses unknown fields and malformed hashes, and turn the update report of the flasher, the result record of the tester and a line of the install log of the updater into it without changing them; `docs/EVIDENCE.md` describes it and `vendor_copy.py` has the set `evidence`.
- **The compatibility matrix can be read by a program:** `generated/compat.json` is written (and checked) by `tools/compat_table.py` from `spec/versions.json`, and `urtc_common.compat` compares it with the folders next to a program: one row per project (as released, newer, older, not installed or version unknown, never a match when the version cannot be read), the copy of the shared code each carries, and the firmware that URTC-FLASHER and URTC-WEB-STUDIO bundle against the firmware of the tool head repository. `compat_qt.CompatModel` and `qml/CompatDialog.qml` show it read-only in the eight languages; `vendor_copy.py` has the sets `compat_data`, `compat_qt` and `compat_qml`.

- **Related Projects lists the URTC family:** the section names the repositories of URTC by group, each with one short line about what it is for, and, in one short line each, the sister projects (independent ecosystems of the same author that share the base and the tools), in the eight languages. It no longer says that URTC is part of another ecosystem.
- **The README follows the universal layout in the eight languages:** the sections are in the fixed order with their fixed names, the Architecture and the Repository Structure are drawn from `docs/architecture.json` and `docs/structure.json` by `tools/make_architecture.py` and `tools/make_structure.py`, and the sections for tests, build, roadmap, languages and contributing are new.
- **The layout of the README is checked in the CI:** the validator runs `tools/universal_readme_check.py` and lists, as a warning, what differs from the universal layout of the README.
- **Project status is the second section of the README,** right after At a glance, in the eight languages.
- **The shared README sections go where the universal layout wants them:** Project status right after At a glance with the traffic-light icon, and How it updates, Several tool heads on one bus, First run without hardware and Requirements & compatibility as parts of Architecture, Features and Quick start once a README has those sections (before that they stay where they were); the eight languages of a repository always agree on the place.
- **Downloads are hardened further:** a redirect is followed only to another allowed https host (never to plain http or to a host outside the list), the bytes really written while extracting a package count towards the size limit (not only the size the archive announces), and the folder of a newly created record-signing key is private to the person. Negative tests cover each rule.
- **A shared byte ring for the firmware:** `firmware_base/urtc_ring.h` is the single-producer / single-consumer ring that a receive interrupt fills and the main loop empties (release/acquire indices, power-of-two size, a count of dropped bytes), with its rules tested one by one and, on a POSIX host, by a real producer thread against a real consumer thread. A firmware repository copies it with `vendor_copy.py sync TARGET --set firmware_ring`.

## [0.0.8] - The serial line of the rack in the model and in the vectors and the table of what has run and what is pending is generat

### Firmware and protocol

- **The serial line of the rack in the model and in the vectors:** `rack_sim.StreamDeframer` finds the frames in a stream of bytes the way `rack_deframer.c` of the rack firmware does (start byte, version, length, CRC, resynchronisation from the next start byte it already holds, the silence timeout with its wrap-safe clock, the six counters), and `SimulatedRack.receive_stream(data, now_ms)` feeds what a serial line delivers to the rack. `conformance/rack_vectors.json` and `generated/rack_vectors.h` carry 19 streams (bursts with their times, the frames that come out and the final counters) that the firmware passes through its real deframer and the model passes too; 3 more tests, the numbers of a few streams typed by hand besides.
- **The tool table of the firmware document is generated:** `tools/generate_tools_doc.py` writes the table of the 25 profiles (identifier, name, kind, range, watchdog, expansion board) of `docs/TOOLS.TXT` of the firmware repository from `spec/tools.json`, between markers that carry the digest of the block like the CAN document does, and checks that the sections of the prose are numbered like the identifiers and name the same expansion board as the profile (none, recommended or required). 9 tests; the nightly comparison runs them against the firmware repository.
- **The whole version of the slave application on the bus:** `0x222` takes an optional third byte, the low byte of the minor number (the 8-byte answer to `0x221` stops at the high byte of the minor, so no frame carried the low one and the programs showed `0.?.5`). The frame is 2 or 3 bytes long; a program that reads two bytes still gets the patch, and a master or a slave from before the byte behaves as it did. `parse_slave_app_version` joins the high byte of the answer with the third byte of the companion into the minor, and `slave_app_version_text` shows `0.2.4`; `slave_version_vectors.json` gained seven cases (the low byte, a minor of 0, a minor above 255, the companion first, the longer answer winning, the two-byte companion, an invalid patch).
- **A window to find the tool heads of a bus and select one, written once for the programs:** `node_picker.py` (the rules: one row per head with a state a person can read, namely ready, selected, address conflict, fault latched, in its bootloader or lost; the switch of the extension read from `0x1AD` and said when it is off, saved but waiting for a power-up, or unknown; a confirmation before anything is selected; `GatedTransport`, which refuses a single-head frame while several heads are on the bus and none is confirmed selected, lets the frames of the extension through and lets the bootloader frames of a head pass once the enter-bootloader frame went out), `node_picker_strings.py` (50 texts in the eight languages, also in the catalog of the web studio as `nodes.*`), `node_picker_qt.py` and `qml/NodePickerDialog.qml` (the window; finding and selecting run in a thread), `conformance/node_picker_vectors.json` (made by `tools/make_node_picker_vectors.py`; the web studio holds its TypeScript to the same file), a section of the quick guide of the flasher and the tester in the eight languages, and `sim_picker`, a picker over the modelled bus for tests and pictures without boards. Not tried on boards.
- **A head that stops being confirmed while it is driven is released, by default:** `MultinodeHost.tick` notices that the selected head is gone, in conflict, faulted, in its bootloader or no longer reports itself selected, forgets the selection, records a `Lapse` and, with `release_on_lapse` (on by default, a checkbox of the window), sends SAFE_STOP so no head keeps an output on without a host watching it; with it off the host still forgets the selection and says that the outputs were left as they are. `suspend` covers the head that is about to reset into its bootloader. Whether the firmware should also let go of its outputs when a selection lapses is a decision that is still open.
- **The version of the slave application as the host reads it:** `versioning.parse_slave_app_version` joins the answer to `0x221` for register `0x01` with its `0x222` companion (major, patch; the 8 bytes of the answer stop at the high byte of the minor field, so the minor shows as `?` unless a longer answer carries it), `slave_app_version_request`, `slave_app_version_text` and `conformance/slave_version_vectors.json` (set `slave_version`).
- **`0x222` SLAVE_APP_PATCH and the patch number in the slave version register:** the tenth byte of the version register of the slave application (reserved until now) carries its PATCH number; the master passes it on in the new companion frame `0x222` (register, patch 1 to 127) after the `0x221` answer, and a byte of 0 sends nothing, so an older slave behaves as before. The specification, the constants, the vectors, the protocol table and the identifier count (96) follow. The notes of `0x7FD` and `0x7FE` say that the bootloader answers them only in a session that the application started by accepting `0x7F0`, or when no valid application is installed.
- **Scenarios, a model of the nodes and a host session for several heads on one bus:** `conformance/multinode_scenarios.json` (written by `tools/make_multinode_scenarios.py` with the expectations typed by hand from `docs/MULTINODE.md`, 14 scenarios of one node: listening, hearing another node, selection and its lapse, conflict, safe stop, the node command, discovery spacing, a reported fault, the wrap of the millisecond counter) and the same as C tables (`generated/multinode_scenarios.h`) that the firmware replays against `multinode.c`. `urtc_common.multinode_sim` models the nodes and a bus that joins them and is held to the same scenarios; `urtc_common.multinode_host` finds the heads, selects one and waits for its own status to say so, repeats SELECT before it lapses, refuses to send a single-head frame (and above all a bootloader frame) to a head it has not confirmed, refuses a head in conflict, with a fault, gone or in its bootloader, and passes frames through unchanged on a bus where nobody answers. `vendor_copy.py` has the sets `multinode` and `multinode_c`. Not tried on boards.
- **The reference half of the CAN document of the firmware is generated:** `tools/generate_canbus_doc.py` writes the index of identifiers, the field layouts with their examples, the tool profiles, the enumerations, the constants, the magic payloads, the slave registers, the procedures and the multinode frames between marker lines at the end of `docs/CANBUS.TXT` of the firmware repository, and leaves the prose untouched; the digest of each block is in its marker, so a hand edit is found with no specification at hand (`--check` compares with the specification). A new identifier reaches the document by one run of the tool.
- **Two texts for the rack bench of the web studio** in the catalog, in the eight languages: the minimum interval between commands and the notice of a command held back.
- **A model of the fault recorder and the scenarios the firmware replays:** `blackbox.Recorder` is what `BlackBox_Sample` does every tick (a ring of 67 samples, one flush per rising edge of the error flag, the latch re-armed when it falls, the flags with the end-stop, the error and the thermal guard code), written independently of the C code. `conformance/blackbox_vectors.json` carries seven scenarios (no fault, the first fault, a fault after the ring wrapped, a fault that stays raised, a second fault after the latch is re-armed, the flags, the wrap of the tick counter) with the ticks after which a record must have been written and the 678 bytes of the last one; `generated/blackbox_vectors.h` is the same as C tables (`vendor_copy.py --set blackbox_c`) for the firmware repository to replay against `firmware_blackbox.c`.
- **The frame layer and the rate limiter of the serial links, written once:** `firmware_base/urtc_frame.h` decides whether a buffer holds one good frame (incomplete, start byte, version, length, CRC, in that order) and builds the other direction (`urtc_frame_start`, `urtc_frame_seal`) for a format given as data (start byte, version, position of the length byte, longest payload); the rack frame (length at index 4) and the vision sensor frame (length at index 8) were two copies of the same code. `firmware_base/urtc_rate_limiter.h` is the minimum interval between accepted messages, right across the wrap of the 32-bit millisecond counter. `src/urtc_common/frame_layer.py` is the reference of both; `conformance/rate_vectors.json` and `generated/rate_vectors.h` carry the decisions of the limiter (`make_extra_vectors.py --check` in the CI), and `tests/c/test_frame_layer.c`, compiled with the host compiler (with the sanitizers) by `tests/test_frame_layer.py`, holds the headers to every parse vector of the rack and of the sensor, rebuilds every vector frame byte for byte and passes the rate vectors. `vendor_copy.py` has the sets `firmware_frame` and `rate_c`.
- **`firmware_base/urtc_test.h`:** the `TEST_ASSERT` macro of the host-side firmware tests, which the rack, the vision tool and the tool head firmware each defined in their own `test_runner.h`; copied with `vendor_copy.py --set firmware_test`, and a test compiles it with the host compiler and checks that a failed assertion is counted.
- **A virtual board behind an SLCAN adapter on a TCP port:** `virtual_board.py` (`python -m urtc_common.virtual_board`, or `urtc-common virtual-board`) listens on the loopback interface and speaks the SLCAN subset of the real adapters: bit rate, open, listen-only, close, version and status queries, a bell for what it does not understand, `z` after an accepted transmit, and no transmit from a closed or listen-only channel. Behind it the board answers the version query with the patch frame, answers the active-tool query with the quick state, enters the bootloader on `0x7F0` carrying exactly the magic payload and plays the update exchange of the simulated bootloader. Its answers are held to the shared vectors (version queries, quick states, magic payloads) by the tests. With `--exec` the same text is bridged to a program that reads one SLCAN line per frame, such as the virtual board of the firmware repository, so the real receive path can sit behind the same port.
- **`transports.SLCAN` opens a pyserial URL:** a port such as `socket://127.0.0.1:7777` goes through `serial_for_url`, so the flasher, the tester and the gateway reach the virtual board with no adapter (`transports.is_serial_url`); a module that cannot open URLs, or a URL that does not open, is a typed error.
- **The sensor frame of the vision head has a reference and vectors:** `sensor_frame.py` encodes and parses the frame (start byte `0xB6`, timestamp, CRC-8) and validates the thermal reading; `conformance/sensor_vectors.json` and `generated/sensor_vectors.h` are written by `make_extra_vectors.py` (`--check` in the CI) for the vision firmware to be held to. New `vendor_copy.py` sets: `virtual_board`, `sensor`, `sensor_c`.
- **The rack serial frame and the sensor frame are big-endian, version 2:** the temperature of the pre-heat command and the timestamp and thermal reading of the sensor frame were little-endian, unlike every other multi-byte value of the family. Both frames now carry version 2, so a receiver refuses a frame of the old layout as an unsupported version instead of reading another number. `rack_sim.py`, the rack vectors and the CRC-8 check case follow; `docs/CONTRACTS.md` has a section on the companion links, a test compares it with the module, and a test reads the prose of the firmware repository for the same two versions. The CAN protocol of the tool head is unchanged.

### Tests, builds and checks

- **The table of what has run and what is pending is generated:** `tools/status_table.py` reads the `maturity`, the `evidence` level and the `notes` of the manifest of each repository next to this one, copies the clauses of the notes that say something was never run or is not done yet into `spec/status.json`, and writes `docs/STATUS.md` from it (with `--check` in the CI and, with `--siblings`, in the nightly comparison, which fails when a manifest says something else than the file). Below the bench level a run on a real board is always listed as pending. The README files name it in the eight languages. 10 tests.
- **A type check on every push, and the development lock written for the Python the CI runs:** `mypy` checks `urtc_common` and `urtc_ui` (a step of the CI; 14 findings fixed with annotations where the generated tables are read, no behaviour changed) and is part of the pinned development dependencies. `requirements-dev.lock` is regenerated with hashes for Python 3.12 (`uv pip compile --universal --python-version 3.12`), so what that Python needs is in it and what only another Python needs carries a marker; it replaces the lock of Python 3.14 that had been patched by hand.
- **The specification as an installable package:** `tools/make_release_artifacts.py` builds, signs and checks the three files a release attaches: a Python wheel (`urtc-common`, not published on PyPI), a source archive and the generated C header `urtc_can_ids.h`, each with a `.sha256` and an Ed25519 `.sig` by the key of the releases (the one the programs already trust). The build is reproducible (sorted entries, fixed times, a stored wheel, fixed compression); `verify` checks hashes, signatures, the `RECORD` of the wheel and the header inside it, `smoke` unpacks the wheel apart and runs the shared vectors from it, `reproduce` builds twice and compares. The wheel carries the specification, the tool table, the header and the vectors as data, found by `urtc_common.specdata` (the checkout wins when the package runs from one) and listed by `urtc-common files`. The guide is `docs/PACKAGE.md`; nothing is published and no version changes.
- **One source for the language files of the programs:** `spec/i18n/catalog/` holds the texts of the flasher, the tester, the web studio and the updater in the eight languages (the texts the glossary names are references to it) and `tools/i18n_generate.py` writes the `.lng`, `.json` and `.py` files of each program, with a lock (`urtc_i18n.lock.json`) and a test of its own in the program (`tests/test_i18n_generated.py`, `src/locales/generated.test.ts`); `check` fails when a file is not what the catalog generates and runs in the nightly comparison. Moving the programs onto it removed lines that no reader used (a stray sentence in the flasher files) and made the line break of the saved black box label what its code expects (the paths of the two files).
- **A static check on every push:** `ruff.toml` (unused names, exception chaining and syntax errors, the rules the flasher and the tester already ran) and a step of the CI that runs `ruff check .` with a pinned ruff; it found four unused imports and an f-string without placeholders, now fixed.
- **A glossary for the phrases several programs say (`spec/i18n/glossary.json`):** 94 phrases (Close, Refresh, Clear, Heater PID, Port search, Browse ...) written once in the eight languages with the keys of the flasher, the tester, the web studio and the updater that must say them that way. `tools/i18n_glossary.py` checks the file (eight languages, same placeholders, known programs), compares it with the programs next to this repository (case, accents, punctuation and the AE/OE/UE of a title in capitals are forgiven; a different word is not) and rewrites the lines of the `.lng` and `.json` files that differ, keeping a title in capitals in capitals; `tests/test_i18n_glossary.py` runs it on the programs and the nightly comparison clones the updater too. The first run found and fixed 25 differences, among them a German `Löschen` next to `Leeren`, `Heizer-PID` next to `Heizungs-PID`, two Portuguese ways of saying the automatic detection and a missing letter in a German title of the updater.
- **Self-update from a signed package (`self_update.py`):** the whole flow of a program that updates itself from a GitHub release, with no network and no window of its own (the caller passes the fetch and the progress callback) and standard library only. `find_update` offers only a strictly higher version (three or four components) that has a package for the platform, never a draft or a pre-release; `download_package` takes the package, its `.sha256` and its `.sig` only over https from the hosts of GitHub release downloads, checks the announced size and the SHA-256, and leaves no partial file behind when it fails; `verify_package` checks the Ed25519 signature of `urtc-pkg/1|app|version|platform|sha256|size` against the key pinned in the program and the key identifier the release declares; `safe_extract` reads a `.zip` or `.tar.gz` without ever writing outside the folder (no `..`, absolute path, drive letter, link or device) and within limits of size and file count; `install_package` refuses while a bus operation is running, checks the `app_info.json` of the package against what was announced, switches `current.txt` and keeps the two latest releases; `rollback` and `finish_first_start` go back to the previous release, the second by itself when the first start of the new one fails; every step is appended to `history.jsonl`. The Ed25519 check is tested against the RFC 8032 vector and the whole flow against a fake server (32 tests); `vendor_copy.py --set update` copies it. No program uses it yet.

## [0.0.1] - The CAN protocol as data

- **Specification:** `spec/can_protocol.json` (format 1, with its JSON Schema) describes all 88 identifiers of the tool-head bus: direction, who handles each, the tools it is valid for, the length rule and the typed layout of every request and response, the gates (critical error, boot sequence, magic payload), the watchdog and telemetry timing, 16 enumerations, 37 constants, the four magic payloads, the 23 registers of the expansion slave, the version procedures and the SLCAN subset. Every entry records which of the firmware, URTC-FLASHER, URTC-TESTER and URTC-WEB-STUDIO define it, so the gaps are explicit: `0x220`, `0x221`, `0x1A8` and `0x1A9` exist in the firmware and in no host (the last two are not in the protocol prose either), and `0x220`/`0x221` carry a note about the missing allow-list.
- **Generated code:** `tools/generate_constants.py` writes a C header, a TypeScript module and a Python module from the specification, with the constants, the tables and one pure builder and one pure parser per layout, and `docs/PROTOCOL_TABLE.md`. `--check` writes nothing and fails when a file is out of date. Builders refuse an out-of-range value, a value outside a closed enumeration and a wrong magic payload instead of clamping them; parsers report a byte that older firmware does not send as absent, never as zero.
- **Conformance vectors:** `conformance/can_vectors.json` keeps the nine sections that the flasher, the tester and the web studio already share, unchanged, and adds an encode and a decode vector for every layout, the legacy short forms, the encodes that must be refused, the full identifier list and SLCAN byte streams (extended frames, remote frames, glued status characters, noise, a split line). `tools/make_conformance.py` writes them with a packer of its own, independent of the generated encoder, and checks the hand-written example bytes of the specification against it.
- **Python package:** `urtc_common` holds the SLCAN codec (strict hexadecimal, standard data frames only), a classic-frame type, the version and quick-state readers, a runner for the vectors and a small command line. The transports (SLCAN serial, SocketCAN, python-can and a simulated board, plus listen-only bitrate detection) are extracted from the two copies the flasher and the tester kept and merged so that each fix of either copy applies once; they take their serial port, socket and python-can module as parameters, so they are tested with fakes.
- **Comparison with the other repositories:** `tests/test_siblings.py` reads the text of the firmware, the flasher, the tester and the web studio, when they are checked out next to this repository, and fails when an identifier, a magic payload, a tool or status table, a length check, a gate, a limit, a register or the list of identifiers of the protocol prose stops agreeing with the specification. It skips when they are absent: nothing depends on those repositories.
- **Copies for other repositories:** `tools/vendor_copy.py` copies chosen parts into another repository with a lock file of SHA-256 sums, and its `check` fails when a copy was edited by hand or fell behind. Nothing in the other repositories uses it yet; `docs/MIGRATION.md` lists the order in which each can.
- **Documents:** `docs/CONTRACTS.md` (the contract, who implements what, the known gaps and differences, the rules for change), `docs/SPEC_FORMAT.md`, `docs/MIGRATION.md` and the generated `docs/PROTOCOL_TABLE.md`; the README in eight languages.
- **CI:** the baseline workflow runs the shared validation, the generator checks and the tests on Linux and Windows; a nightly workflow runs the comparison with every repository of the ecosystem fetched next to this one.
